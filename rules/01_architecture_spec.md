# ARCHITECTURE 蓝图规范

本文档定义项目架构蓝图 `ARCHITECTURE.md` 的结构和内容规则。架构蓝图是项目的"宪法"，所有下游 worker 执行任务时都会引用它。

---

## 核心原则

1. **唯一真相源**：项目中所有架构级决策，只在这份文档里定义，不散落在各个 Task Card 里。
2. **显式优于隐式**：凡是 worker 可能需要猜的事情，都必须写出来。
3. **可验证**：每一条约定都能被机器检查或被 reviewer 明确判断。
4. **禁用模糊词**：不出现"适当"、"合理"、"良好"、"必要时"、"尽量"这类词。

---

## 文档结构（必须全部包含）

### 1. 项目目标

一段话（3-5 句）说清楚：
- 这个项目是什么
- 给谁用
- 解决什么问题
- MVP 的边界在哪里

### 2. 技术栈

分项列出，每一项都要带**版本号**和**选择理由**（一句话即可）：

- 前端框架：
- UI 库 / CSS 方案：
- 后端语言 / 框架：
- 数据存储：
- 关键第三方依赖：
- 构建工具：
- 测试框架：
- **明确排除**：列出本项目**不使用**的技术（防止 worker 自己引入），例如"不使用 Redux"、"不引入额外的 UI 组件库"

### 3. 目录结构

用树状图展示完整目录，每个目录附一句话说明：

```
project/
├── src/
│   ├── components/    # 可复用的 UI 组件
│   ├── pages/         # 页面级组件，对应路由
│   ├── ...
├── tests/             # 测试代码
└── ...
```

规则：
- worker 新增文件时必须放入对应目录
- 没有合适目录时不允许自创新目录，必须回到规划阶段讨论

### 4. 数据模型

列出所有核心实体。推荐用 TypeScript interface 或表格：

```typescript
interface User {
  id: string;          // UUID
  email: string;       // 唯一，小写
  createdAt: Date;
  // ...
}
```

必须包含：
- 字段名、类型、约束
- 实体间关系（一对多 / 多对多）
- 如果有数据库，对应表名和索引

### 5. API 约定（有后端时必写）

- **路径风格**：RESTful / RPC / GraphQL，选一种
- **命名规则**：`/api/v1/users` 还是 `/users`
- **认证方式**：JWT / Session / API Key / 无
- **错误响应格式**：统一结构，例如：
  ```json
  { "error": { "code": "NOT_FOUND", "message": "..." } }
  ```
- **成功响应格式**：统一结构
- **典型请求/响应样例**：至少给 1-2 个完整示例

### 6. 命名约定

- 文件名：kebab-case / snake_case / PascalCase
- 组件名：PascalCase
- 函数 / 变量：camelCase / snake_case
- 常量：SCREAMING_SNAKE_CASE
- CSS 类名：kebab-case / BEM / 其他
- Git 分支：`feat/xxx`、`fix/xxx`、`task/T-xxx`
- Commit 信息：Conventional Commits 还是自由格式

每一项都要给一个具体示例。

### 7. 代码风格与工具链

- Lint 工具和配置（eslint / prettier / ruff 等）
- Format 工具
- Type check（tsc / mypy）
- 每次提交前必须通过的命令：例如 `npm run lint && npm test`

### 8. 测试要求

- 测试框架
- 每个任务**必须**包含什么级别的测试（单元 / 集成 / E2E）
- 覆盖率目标（如果有）
- 测试文件存放位置和命名

### 9. 关键约束与禁止事项

Worker 在执行任务时**明确不允许**做的事：

- 不允许修改的路径：`config/**`、`.github/**` 等
- 不允许引入新的 npm 依赖（除非 Task Card 明确授权）
- 不允许修改现有 API 的输入输出格式
- 不允许跨 Epic 改动代码
- 不允许删除现有测试
- ...

### 10. Epic 划分

把项目切成 5-15 个功能模块（Epic）。每个 Epic 一行：

```
E1 - 用户认证：注册、登录、JWT 签发与校验 — 预计 4-6 个 Task
E2 - 产品列表：分页、筛选、排序 — 预计 3-5 个 Task
E3 - ...
```

规则：
- Epic 之间应尽量**弱耦合**
- 标注 Epic 之间的依赖关系（哪个必须先完成）
- 每个 Epic 预计 3-10 个 Task

### 11. 任务执行通用规范

所有下游 Task Card 都遵守的默认值：

- 单任务 diff 行数上限：默认 500 行，目标 < 200 行
- 单任务预计时长：15 分钟 - 2 小时
- 提交前必须通过的检查清单（lint / typecheck / test）
- Task Card 的文件位置：`plans/T-xxx.md`
- Worker 工作分支命名：`task/T-xxx`

### 12. 环境与部署（如果适用）

- 开发环境要求（Node 版本、Python 版本等）
- 环境变量清单（`.env.example` 的字段）
- 本地运行命令
- 部署目标（本地 / Vercel / 自有服务器 / 暂不部署）

## 产出后的检查清单

架构蓝图产出后，对照检查：

- [ ] 每一节都有内容，没有"TBD"或"待定"
- [ ] 技术栈每一项都有版本号
- [ ] 目录结构中每个目录都有用途说明
- [ ] 命名约定每一项都有示例
- [ ] Epic 数量在 5-15 之间
- [ ] 全文无"适当"、"合理"、"良好"、"尽量"等模糊词
- [ ] Worker 看完这份文档后，能回答："我能改哪里？不能改哪里？"
