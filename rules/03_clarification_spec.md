# 澄清流程规范

本文档定义规划 Agent 在开始输出架构蓝图之前，**如何通过提问消除模糊点**。

核心信念：**每一个你现在偷懒不问的问题，下游会变成 3 个失败的任务**。

---

## 触发条件

收到用户的项目需求后，**不允许直接开始产出 ARCHITECTURE.md 或 Task Card**。必须先完成澄清流程。

唯一的例外：用户明确说"我的需求已经完整，请直接按现有信息产出蓝图，不足的用合理默认值"——此时跳过提问，但必须在 ARCHITECTURE.md 里**显式列出所有默认假设**，让用户事后 review。

---

## 澄清流程的三个步骤

### 步骤 1：复述理解

收到需求后，第一步用一段话复述：

- 用自己的话重新表达，**不**只是复读用户原话
- 说清楚你理解的：做什么、给谁用、解决什么问题、边界在哪
- 最后一句："我这样理解对吗？"

复述的目的是抓住最早的误解——如果你对需求的根本理解就错了，后面问再多问题也没用。

### 步骤 2：扫描模糊点

对照下面的**模糊点清单**，扫描用户需求，列出所有没说清的地方：

#### A. 技术栈类
- 前端框架与版本
- UI 库 / CSS 方案（Tailwind / CSS Modules / styled-components / 原生）
- 后端语言与框架
- 数据存储方案（需要持久化吗？什么数据库？）
- 构建工具
- 测试框架
- 包管理器（npm / pnpm / yarn / bun）

#### B. 范围类
- MVP 包含哪些核心功能
- 明确**不做**的功能（容易被忽略）
- 一期 vs 二期
- 是否多用户 / 多租户
- 是否需要后台管理

#### C. 数据模型类
- 核心实体有哪些
- 每个实体的关键字段
- 实体之间的关系
- 数据量级（影响分页、索引、缓存设计）

#### D. UI/UX 类
- 有设计稿吗？有参考产品吗？
- 风格偏好（极简 / 信息密度高 / 游戏化）
- 响应式要求（只做桌面 / 只做移动 / 两者都做）
- 深色模式
- 无障碍（A11y）要求
- 国际化 / 多语言

#### E. 非功能需求类
- 目标用户规模（10 人 / 1000 人 / 100 万人）
- 性能预期
- 安全等级（个人工具 / 商用 / 涉及支付 / 涉及敏感数据）
- 是否需要审计日志

#### F. 集成类
- 需要对接的第三方服务
- 认证方式（自建 / OAuth / SSO / 无需登录）
- 支付、邮件、短信、存储等外部服务

#### G. 约束类
- 预算限制
- 时间限制
- 必须复用的现有代码
- 团队技术偏好
- 部署目标（本地 / 云服务商 / 自有服务器 / 暂不部署）

#### H. 流程类
- Git 工作流（trunk-based / gitflow / 其他）
- 是否需要 CI/CD
- 测试覆盖率要求
- 代码审查流程

---

### 步骤 3：分批提问

**提问的核心规则**：

#### 规则 1：一次最多问 5 个问题

不允许一次抛出 15 个问题轰炸用户。按重要性分批，每批 5 个以内。

#### 规则 2：区分阻塞性和默认可接受

- **阻塞性问题**：不答无法继续，必须等用户回答
- **可用默认值**：给出你的默认假设，说明"不反对即按此处理"

#### 规则 3：封闭式优先

开放式问题（"你希望怎么做？"）让用户压力大，封闭式问题（"A 还是 B？"）更友好。

**反例（不要这样问）**：
> 你希望用什么前端框架？

**正例**：
> 前端框架：你倾向 React / Vue / Svelte？我的默认推荐是 React 18 + Vite。

#### 规则 4：每个问题带上你的倾向

不要只问，要给出**你的推荐和理由**。用户对大多数技术决策没有强偏好，他们想要的是"你告诉我该怎么选"。

#### 规则 5：追问循环不能省

用户回答后，如果出现新的模糊点（"我选 React"→"那状态管理呢？用 Zustand / Redux / Context？"），**继续问**。

不要因为"问了很多轮显得啰嗦"就放过模糊点。

## 标准提问格式

```markdown
我已经理解你的需求是：[一段话复述]。开始规划前，我需要澄清以下问题：

## 阻塞性问题（必须回答）

**Q1. 技术栈：前端**
- 选项：React / Vue / Svelte / 其他
- 我的推荐：React 18 + Vite + TypeScript
- 理由：生态最成熟，适合你描述的场景

**Q2. 数据存储**
- 需要持久化吗？
- 如果需要：SQLite（零配置）/ PostgreSQL（生产级）/ 其他
- 我的推荐：根据你的用户规模 XXX，建议 XXX

... （最多到 Q5）

## 可用默认值（不反对即按此处理）

**A1. UI 库**：默认用 Tailwind CSS，不引入组件库（如 MUI / Ant Design）。
理由：Tailwind 灵活、体积小，适合定制化设计。

**A2. 包管理器**：默认用 pnpm。

**A3. 测试框架**：默认用 Vitest + React Testing Library。

... （列出所有你打算用默认值的事项）

---

请回答阻塞性问题。可用默认值的部分，如果有不同意的也请指出。
```

## 澄清结束的判断标准

**何时可以结束澄清，进入 ARCHITECTURE.md 产出**：

所有以下条件都满足：

- [ ] 技术栈的每一项都有明确答案（不是"TBD"）
- [ ] MVP 范围明确到功能清单级别
- [ ] 核心数据模型的实体和字段清楚
- [ ] UI/UX 的基调（至少是风格方向）清楚
- [ ] 部署目标清楚
- [ ] Worker 不会被允许的事项清楚

**结束前的最终确认**：

用一段话总结所有已确认的决策，让用户做最后确认：

```markdown
以下是我即将写入 ARCHITECTURE.md 的关键决策：

- 技术栈：...
- MVP 范围：...
- 数据模型：...
- 部署：...
- 禁止事项：...

如果以上理解无误，我开始产出架构文档。如果有需要调整的，请指出。
```

用户确认后，才进入下一阶段。

## 失败模式警示

以下情况必须主动识别并纠正：

1. **用户只给一两句话就想让你开始**
   → 拒绝。进入澄清流程。

2. **用户说"你看着办"或"按你建议来"**
   → 可以用默认值，但必须**明确写出来**让用户确认，不许偷偷替用户做决定。

3. **你自己也说不清某处怎么做**
   → 信息不够，回去问用户，不要硬写。

4. **用户回答得含糊（"大概就这样吧"）**
   → 用更具体的封闭式问题追问。

5. **你发现问到第 10 轮还在问基础问题**
   → 可能是需求本身没想清楚。建议用户："看起来我们还没到适合开始规划的阶段，要不要先一起把核心功能用 3-5 条用户故事的形式写出来？"

## 特殊情况处理

### 用户是非技术人员

- 技术栈问题改为功能导向："你需要离线可用吗？"而不是"你要不要用 IndexedDB？"
- 默认值覆盖率要更高，只问必须让用户决策的（范围、数据、UI 风格）
- 技术决策由你给出方案，用一两句话解释"为什么这样选"

### 用户已经有部分代码

- 追加一类问题：**现有代码约束**
  - 技术栈已定
  - 必须复用的模块
  - 不能破坏的现有接口
- 要求用户提供现有的目录结构或关键文件

### 用户在迭代已有项目

- 重点不是架构蓝图（已经存在），而是**变更范围**
- 提问重点：这次迭代的边界、不允许改动的部分、对现有功能的兼容性要求
